# chopin 主线移植：Linux 7.3.4 内核 + Debian 13 / GNOME

面向 **Redmi Note 10 Pro 5G / POCO X3 GT（代号 chopin，MT6891Z/CZA）** 的 Linux 主线内核移植工作区。

| 项目 | 内容 |
| --- | --- |
| 设备 | Redmi Note 10 Pro 5G / POCO X3 GT（chopin） |
| SoC | MediaTek MT6893（Dimensity 1100/1200 系列，设备标识 MT6891Z/CZA） |
| 内核基线 | **Linux v7.3.4**（stable，commit `98385cc`） |
| 参考实现 | [MT6891-Mainline](https://github.com/MT6891-Mainline) 的 `7.3.3-mt6893-xiaomi-chopin` 分支（18 个补丁） |
| 移植方式 | 以 v7.3.4 为基线，逐个 `git am` 移植参考分支补丁（全部干净应用，无冲突） |
| 当前状态 | **Debian 13.7 + X11 GNOME 桌面已在实机运行**（llvmpipe，1080×2400，串口/SSH 正常）；触摸与 GPU 待修 |

> 技术文档：[docs-kernel.md](docs-kernel.md)（引导链、设备树、cmdline、驱动状态、已知问题、刷写）。
> 用户空间（Debian 根文件系统、桌面、initramfs、网络安装）已从本工作区移除，另行交给系统专家处理。

当前 `chopin` 分支已打标签 `chopin-v7.3.4-r1`，作为本次移植的里程碑。

- 日常工作在 `chopin` 分支，`main` 永远保持与上游 v7.3.4 一致，便于 `git rebase` 或对比 diff。
- 本项目仓库（`/root/MT6891-Mainline`）只跟踪 `patches/`、`scripts/`、`README.md`，`linux/` 通过 `.gitignore` 排除，避免两套历史互相污染。

常用操作：


### 构建结果

| 产物 | 路径 | 大小 |
| --- | --- | --- |
| 未压缩内核 | `linux/arch/arm64/boot/Image` | 57 MB |
| 压缩内核 | `linux/arch/arm64/boot/Image.gz` | 18 MB |

## 6. 打包 boot 镜像

```bash
cd /root/MT6891-Mainline
python3 scripts/mkbootimg.py \
  --stock /mnt/d/MT6891-Mainline/chopin/images/boot_a.img \
  --kernel linux/arch/arm64/boot/Image.gz \
  --dtb    linux/arch/arm64/boot/dts/mediatek/mt6893-xiaomi-chopin.dtb \
  -o       out/boot-chopin-mainline.img
```

脚本读取原厂镜像的头部（page size、各段地址、os_version、cmdline），只替换 kernel/dtb 并重算 SHA1 id，实测生成的镜像：

- header v2，page size **2048**
- kernel_addr `0x40080000`，ramdisk_addr `0x51100000`，tags_addr `0x47c80000`
- kernel 18,174,533 B + 原厂 ramdisk 21,525,454 B + dtb 281,602 B → 39 MB

产物同时导出到 Windows 侧 `D:\MT6891-Mainline\out\`（`Image.gz`、dtb、boot 镜像、`SHA256SUMS`），可直接在 Windows 的 fastboot 环境刷写。

刷写（**会覆盖 boot 分区，务必先备份**）：

```bash
adb reboot bootloader
fastboot flash boot out/boot-chopin-mainline.img
fastboot reboot
```

## 7. 已知限制与后续工作

1. **实机验证情况**：见第 9 节的启动记录；USB gadget（mtu3 / g_multi）仍未打通，
   细节与证据在 [docs-kernel.md](docs-kernel.md) 第 5.2 节。
2. **引导链**：chopin 的 dtb 由 bootloader 从 `dtbo` 分区加载，原厂 `boot_a.img` 头部 `dtb_size=0`。上面脚本把 dtb 追加进 boot 镜像只是通用做法，MTK LK 是否采用需实测；参考项目走的是 UEFI（[Mu-Silicium](https://github.com/MT6891-Mainline/Mu-Silicium)）路径，用 `Image` + `dtb` 从 ESP 引导，更接近主线玩法。
3. **用户空间**：原厂 ramdisk 与主线内核的模块布局不匹配，要真正进系统需要自建 initramfs（postmarketOS / Alpine）。
4. **固件**：触摸（Novatek）需要 `/lib/firmware` 下的镜像文件；WLAN、音频 DSP、相机等同样依赖厂商固件。
5. **告警与规范**：厂商 DTS 不符合主线 binding，若要上游化（`git send-email`），需拆分成可评审的小补丁并补齐 binding 文档。

## 9. 实机启动记录（2026-11-14）

设备：chopin（M2104K10AC，Android 13，bootloader 已解锁，slot `_a`）。

### 引导链实况（比文档里写的复杂）

- LK 从 **boot 镜像的 dtb 段**读基础 DTB（该段是 DTBO 表封装，原厂 201,848 字节），再叠加 **dtbo 分区**的 overlay（72,879 字节）。
- 内核在 `setup_machine_fdt()` 里用**内嵌的 `arch/arm64/kernel/chopin-board.dtb`**（256,811 字节，由 `chopin-*.dtsi` 编译）覆盖 LK 传来的 FDT —— 所以改 `mt6893-xiaomi-chopin.dts` 只影响 LK 阶段，运行时 DT 由那组 dtsi 决定。

### 三次启动失败与修复

| 现象 | 根因 | 修复 |
| --- | --- | --- |
| LK 打印 `DRI CMDLINE overflow` 后重启 | 把完整 DTB 塞进 dtbo 分区；同时 DT 的 `/chosen/bootargs` 有 1 KB 厂商 cmdline，LK 追加自己的内容后溢出缓冲区 | 恢复原厂 dtbo；删掉 DT 里的 bootargs |
| 卡 Redmi logo，静默重启 | 同上，LK 在 `load_lk_dtb` 阶段 panic（expdb 里可见 `panic: [ERROR] CMDLINE overflow`） | 同上 |
| 卡 logo，pstore 有 `Asynchronous SError` | I2C PDMA 走 `swiotlb` bounce，bounce 区（`0xf6850000`）落在厂商固件保留内存里，CPU 访问触发外部中止 |  cmdline 加 `swiotlb=0`（另加 `iommu.passthrough=1`） |

### 当前可工作的启动配置

```
CONFIG_CMDLINE="console=tty0 swiotlb=0 iommu.passthrough=1 clk_ignore_unused regulator_ignore_unused pd_ignore_unused ignore_loglevel panic=0 ..."
```

- 去掉 `earlycon=mtk8250` 与 `console=ttyS0`：该 UART 被 LK 关闭（`mtk_printk_ctrl.disable_uart=1`），早期控制台写它会卡死。
- 结果：内核进入用户态，DRM 起来（`card0-DSI-1 connected`，1080×2400），fbcon 在屏幕上输出内核日志，USB ACM 串口控制台（`/dev/ttyGS0` → Windows COM10）可用，触摸 `NVTCapacitiveTouchScreen`（event2）正常，UFS 上 `sdc75` = 107 GB userdata。

### 打包脚本修正

`scripts/mkbootimg.py` 之前把 header v2 的 `dtb_size`/`dtb_addr` 偏移写错（应为 1648 的 u32 和 1652 的 u64），导致 `dtb_addr` 变成垃圾值。现已修正，并会自动把裸 DTB 封成原厂同款的 DTBO 表。

### 已知遗留

- i2c5 上部分从设备注册失败（`subpmic_pmic@1a`、`subpmic_ldo@64`、tcpc），WIFI 固件反复重试刷屏。
- `CONFIG_REGULATOR_MT6360` 在 `swiotlb=0` 下不再触发 panic，但 PMIC 调节器功能不完整，长稳还需进一步修 i2c DMA 路径。
